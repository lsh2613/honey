# 작업별 흐름

Phase 4를 실행할 때 이 참조 문서를 읽습니다. Phase 2에서 분류하고 Phase 3에서 확정한 작업(Keep, Update, Consolidate, Replace 또는 Delete)에 해당하는 섹션을 찾아 그 흐름을 따릅니다.

## Keep 흐름

기본적으로 파일을 편집하지 않습니다. 러닝이 여전히 신뢰할 수 있는 이유를 요약합니다.

## Update 흐름

해결책이 여전히 실질적으로 올바른 경우에만 제자리에서 편집합니다.

유효한 제자리 업데이트 예:

- `app/models/auth_token.rb` 참조를 `app/models/session_token.rb` 참조로 이름 변경
- `module: AuthToken`을 `module: SessionToken`으로 업데이트
- 관련 문서의 오래된 링크 수정
- 디렉터리 이동 후 구현 메모 갱신

다음은 제자리 업데이트로 처리하면 안 됩니다.

- 이해에 영향을 주지 않는 오타 수정
- 문체만을 위한 문장 다듬기
- 정확성이나 사용성을 실질적으로 높이지 않는 소규모 정리
- 기존 수정 방법이 이제 안티패턴인 경우
- 시스템 아키텍처가 바뀌어 기존 지침이 오해를 일으키는 경우
- 문제 해결 경로가 실질적으로 달라진 경우

이 경우에는 Update가 아니라 **Replace**가 필요합니다.

## Consolidate 흐름

오케스트레이터가 직접 통합을 처리합니다(문서는 이미 읽었고 병합은 집중된 편집이므로 서브에이전트가 필요하지 않습니다). Phase 1.75에서 식별한 각 클러스터에 대해 다음을 수행합니다.

1. **정본 문서 확인** — 클러스터에서 더 포괄적이고 최신이며 정확한 문서를 선택합니다.
2. **고유 내용 추출** — 정본이 아직 다루지 않는 내용을 피통합 문서에서 가져옵니다. 구체적인 엣지 케이스, 추가 예방 규칙 또는 다른 디버깅 접근법일 수 있습니다.
3. **고유 내용 병합** — 자연스러운 위치에 통합합니다. 단순히 뒤에 붙이지 말고 논리적으로 맞는 곳에 넣습니다. 고유 내용이 작으면(불릿 하나, 문장 하나) 인라인으로 넣고, 상당한 하위 주제라면 명확한 섹션으로 추가합니다.
4. **상호 참조 업데이트** — 다른 문서가 피통합 문서를 참조하면 정본을 가리키도록 바꿉니다.
5. **피통합 문서 삭제** — 보관하지 않고, 리디렉션 메타데이터도 추가하지 말고, 파일을 삭제합니다. Git 기록이 보존합니다.

문서 클러스터에 문서가 3개 이상이면 쌍별로 처리합니다. 가장 많이 겹치는 두 문서를 먼저 통합한 다음, 병합 결과를 다음 문서와 통합할지 평가합니다.

병합 후에는 아래 Replace 흐름의 4단계인 기계적 주장 검사를 정본 문서에 실행합니다. 병합된 내용에는 인용도 함께 들어오며, 통합 과정은 상호 참조가 가장 자주 끊기는 지점입니다.

**병합을 넘어선 구조 편집:** Consolidate에는 반대의 경우도 포함됩니다. 하나의 문서가 검색 시 서로 독립적으로 다루는 편이 좋은 여러 주제를 품어 지나치게 커졌다면 분할을 권장할 수 있습니다. 하위 주제가 실제로 독립적이고 유지보수자가 다른 주제를 읽지 않고도 하나를 검색할 수 있을 때만 수행합니다.

## Replace 흐름

Replace 후보는 한 번에 하나씩 순차적으로 처리합니다. 각 대체 문서는 주 컨텍스트를 보호하기 위해 서브에이전트가 작성합니다.

대체가 필요하면 문서 계약 파일을 읽고 그 내용을 대체 서브에이전트의 작업 프롬프트에 전달합니다.

- `references/schema.yaml` — 프런트매터 필드 및 enum 값
- `references/yaml-schema.md` — 카테고리 매핑
- `assets/resolution-template.md` — 섹션 구조

대체 서브에이전트가 기억에 의존해 프런트매터 필드, enum 값 또는 섹션 순서를 만들어 내게 하지 않습니다.

**근거가 충분한 경우:**

1. 단일 서브에이전트를 생성해 대체 러닝을 작성합니다. 다음을 전달합니다.
   - 기존 러닝의 전체 내용
   - 조사 근거 요약(무엇이 바뀌었는지, 현재 코드가 무엇을 하는지, 기존 지침이 왜 오해를 일으키는지)
   - 대상 경로와 카테고리(카테고리 자체가 바뀌지 않았다면 기존 러닝과 동일)
   - 위에 나열한 세 지원 파일의 관련 내용
2. 서브에이전트는 지원 파일을 사실의 원천으로 삼아 새 러닝을 작성합니다. `references/schema.yaml`은 프런트매터 필드와 enum 값, `references/yaml-schema.md`는 카테고리 매핑 및 배열 항목의 YAML 안전성 규칙, `assets/resolution-template.md`는 섹션 순서의 원천입니다. 전달받은 내용 외에 추가 컨텍스트가 필요하면 전용 파일 검색 및 읽기 도구를 사용해야 합니다.
3. **새 러닝의 프런트매터가 파서 안전한지 검증**하여 문장 규칙이 놓치는 조용한 손상 문제를 잡습니다. 잘못된 `---` 구분선, 스칼라 값의 따옴표 없는 ` #`(조용한 주석 잘림), 따옴표 없는 `: `(조용한 매핑 혼동)를 검사합니다. 번들 검증기는 **스킬 번들 내부**에 있습니다. 런타임 Bash 도구의 CWD는 사용자의 프로젝트이므로 프로젝트 상대 경로로는 찾지 못합니다. 방금 읽은 `SKILL.md`가 있는 디렉터리의 절대 경로를 `SKILL_DIR`에 설정합니다. 이 값은 모델이 채우며 환경 변수가 아닙니다. 실제로 번들 검증기가 없거나 실행할 수 없는 경우에만 수동 검사로 넘어가도록 읽기 가능 여부와 인터프리터 가드를 사용해 실행합니다.

   ```bash
   SKILL_DIR="<absolute path of the directory containing the SKILL.md you just read>"
   if [ -r "$SKILL_DIR/scripts/validate-frontmatter.py" ] && command -v python3 >/dev/null 2>&1; then
     python3 "$SKILL_DIR/scripts/validate-frontmatter.py" <new-learning-path>
   else
     echo "Bundled validate-frontmatter.py is missing or unrunnable; applying the parser-safety checklist manually."
   fi
   ```

   - **스크립트를 실행한 경우:** 종료 코드 0은 파서 안전을 뜻합니다. 종료 코드 1이면 stderr에 문제가 있는 필드가 표시됩니다. 값을 인용하고 문서를 다시 작성한 뒤 종료 코드 0이 될 때까지 재실행합니다. 검증이 실패한 상태에서 성공을 선언하지 않습니다.
   - **스크립트를 실행하지 못한 경우(else 분기):** 검증기의 검사를 정확히 같은 범위로 수동 적용합니다. 더 넓게 검사하면 검증기가 요구하지 않는 편집이 생길 수 있습니다. 위반이 있으면 값을 통째로 인용한 뒤 계속합니다.
     1. 여는 프런트매터 구분선과 닫는 프런트매터 구분선은 각각 내용이 `---`인 줄이어야 합니다(뒤 공백은 허용되지만 `----` 또는 `---extra`는 유효하지 않음).
     2. 이미 인용되었거나 구조화된 값(`"`, `'`, `[`, `{`, `|`, `>`로 시작하지 않음)이 아닌 각 **최상위** 매핑 항목(`key: value`, 들여쓰기 없음)의 값에는 인용되지 않은 ` #`(공백 뒤 해시 — YAML은 이를 주석으로 처리해 조용히 잘라냄)나 인용되지 않은 `: `(콜론 뒤 공백 — 엄격한 YAML에서 중첩 매핑으로 읽힐 수 있음)가 없어야 합니다. 둘 중 하나라도 있으면 전체 값을 인용합니다. 중첩 값, 배열 항목, 이미 인용된 값은 이 검사 범위가 아닙니다(배열 항목 인용은 위 스키마/YAML 안전성 단계에서 처리). 완료 출력에 번들 스크립트를 이 플랫폼에서 사용할 수 없어 검사를 수동으로 적용했다는 사실을 기록합니다.

   검증기는 스키마 규칙을 검사하지 않으며 YAML 예약 표시 문자도 표시하지 않습니다. 예약 문자는 이후 단계에서 큰 소리로 파서 오류를 발생시키므로 조용한 손상 범위 밖입니다. Python 3 표준 라이브러리만 사용하며 PyYAML이나 다른 의존성은 필요하지 않습니다.
4. **후속 문서에 기계적 주장 검사를 실행**합니다. 번들 `scripts/validate-doc-claims.py`는 트리에서 찾을 수 없는 저장소 경로, 해석되지 않거나 도달할 수 없는 커밋 SHA, 해석되지 않는 상대 문서 링크, 남아 있는 초안 스캐폴드("Learning 3", 해석되지 않은 `{{...}}` 토큰)를 표시합니다.

   ```bash
   SKILL_DIR="<absolute path of the directory containing the SKILL.md you just read>"
   python3 "$SKILL_DIR/scripts/validate-doc-claims.py" <new-learning-path>
   ```

   종료 코드 1의 표시는 **실패가 아니라 판정 입력**입니다. 삭제된 코드를 설명하는 후속 문서가 더 이상 존재하지 않는 경로를 인용하는 것은 정당할 수 있습니다. 각 표시는 인용을 수정하거나, 역사적임을 표시하거나, 의도된 것임을 확인하여 처리합니다. 스캐폴드 표시는 항상 수정합니다. 이 플랫폼에서 스크립트를 해석할 수 없으면 같은 패턴을 본문에서 수동으로 검사하고 보고서에 그렇게 적습니다.
5. 서브에이전트가 완료되면 오케스트레이터가 기존 러닝 파일을 삭제합니다. 추적을 위해 새 러닝의 프런트매터에 `supersedes: [old learning filename]`을 넣을 수 있지만 선택 사항입니다. Git 기록과 커밋 메시지만으로도 같은 정보가 제공됩니다.

**근거가 부족한 경우:**

1. 러닝을 제자리에서 stale 상태로 표시합니다.
   - 프런트매터에 `status: stale`, `stale_reason: [what you found]`, `stale_date: YYYY-MM-DD`를 추가합니다.
2. 발견한 근거와 부족한 근거를 보고합니다.
3. 사용자가 해당 영역을 다음에 다룰 때 `compound`를 실행해 달라고 권장합니다.

## Delete 흐름

러닝이 명백히 더 이상 유효하지 않거나, 중복되어 병합할 고유 내용이 없거나, 문제 영역 자체가 사라진 경우에만 삭제합니다. 오래되었다는 이유만으로 삭제하지 않습니다. 나이만으로는 신호가 아닙니다.

연결을 끊기 전에 저장소의 Markdown 콘텐츠 전체에서 최종 인바운드 링크 검사를 실행하여 Phase 1 조사에서 놓친 참조가 없는지 확인합니다. 효율성을 위해 플랫폼의 기본 콘텐츠 검색 도구(예: Claude Code의 Grep)를 우선 사용하고, 전체 파일을 읽기보다 일치 항목 주변의 범위가 지정된 줄을 읽습니다.

각 일치 항목은 삭제 후 끊어질 인용입니다. 정리는 기계적인 작업이며 Phase 2에서 이미 삭제가 올바르다고 분류하고 인용을 확인했습니다. 다시 판단하지 않습니다.

여기서 Phase 1에서 보지 못한 인용이 발견되고 그것이 명백히 장식적인 인용이 아니라면, 중단하고 재분류합니다. autofix 모드에서는 stale로 표시하고, interactive 모드에서는 Replace가 맞는지 사용자에게 묻습니다. 늦게 발견된 모든 인용이 명백히 장식적인 경우에만 정리를 진행합니다.

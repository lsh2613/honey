# Compound Refresh

`docs/solutions/`의 품질을 시간이 지나도 유지합니다. 이 워크플로는 기존 러닝을 현재 코드베이스와 대조해 검토한 뒤, 해당 러닝에 의존하는 파생 패턴 문서를 갱신합니다.

## 모드 감지

`$ARGUMENTS`에 `mode:headless`가 포함되어 있는지 확인합니다. 포함되어 있으면 인자에서 이를 제거하고(나머지는 범위 힌트로 사용) **headless 모드**로 실행합니다.

| 모드 | 시점 | 동작 |
|------|------|------|
| **Interactive**(기본) | 사용자가 있고 질문에 답할 수 있음 | 모호한 경우 결정을 묻고, 작업을 확인함 |
| **Headless** | 인자에 `mode:headless`가 있음 | 모호하지 않은 모든 작업(Keep, Update, Consolidate, 자동 Delete, 충분한 근거가 있는 Replace)을 적용함. 모호한 경우 stale로 표시함. 마지막에 요약 보고서를 생성함. |

### Headless 모드 규칙

- **모든 사용자 질문을 건너뜁니다.** 절대 입력을 기다리지 않습니다.
- **범위 내 모든 문서를 처리합니다.** 범위 힌트가 없으면 범위를 좁히는 질문을 하지 않습니다.
- **안전한 작업을 모두 시도합니다:** Keep(변경 없음), Update(참조 수정), Consolidate(병합 후 피통합 문서 삭제), 자동 Delete(명백한 기준 충족), Replace(근거가 충분한 경우). 쓰기에 성공하면 **applied**로 기록합니다. 쓰기에 실패하면(예: 권한 거부) 보고서에 해당 작업을 **recommended**로 기록하고 계속합니다. 멈추거나 권한을 묻지 않습니다.
- **확실하지 않으면 stale로 표시합니다.** 분류가 실제로 모호하거나(Update와 Replace, Consolidate와 Delete의 구분 등) Replace 근거가 부족하면 프런트매터에 `status: stale`, `stale_reason`, `stale_date`를 추가합니다. stale 표시 쓰기조차 실패하면 보고서에 권장 사항으로 포함합니다.
- **보수적으로 확신합니다.** Interactive 모드에서는 경계 사례를 사용자에게 묻고, Headless 모드에서는 경계 사례를 stale로 표시합니다. 잘못된 작업보다 stale 표시를 우선합니다.
- **항상 보고서를 생성합니다.** 보고서는 핵심 결과물입니다. **Applied**(성공적으로 기록된 작업)와 **Recommended**(전체 근거와 함께 기록에 실패한 작업)의 두 섹션으로 구성합니다. 권한 수준과 무관하게 보고서 구조는 동일하며, 차이는 각 작업이 어느 섹션에 들어가는지뿐입니다.

## CONCEPTS.md 부트스트랩 요청

`CONCEPTS.md`를 생성하거나 부트스트랩하라는 요청으로 구체적으로 실행된 경우(예: "CONCEPTS.md를 만들어 줘", "개념 맵을 만들어 줘", "공유 용어집을 설정해 줘"), 의도가 두 작업 사이에서 모호합니다 — 용어집 파일을 만드는 일과 docs/solutions refresh를 실행하는 일입니다. 진행하기 전에 플랫폼의 차단형 질문 도구를 사용해 구분합니다. Claude Code에서는 `AskUserQuestion`(스키마가 로드되지 않았다면 먼저 `select:AskUserQuestion`으로 `ToolSearch` 호출), Codex에서는 `request_user_input`, Antigravity CLI(`agy`)에서는 `ask_question`, Pi에서는 `ask_user`(`pi-ask-user` 확장 필요)를 사용합니다. 하네스에 차단형 질문 도구가 없거나 호출에 실패한 경우(예: Codex edit 모드)에만 채팅에서 번호 매긴 선택지로 대체합니다. 스키마 로드가 필요하다는 이유로 대체하지 않습니다. 질문을 조용히 건너뛰지 않습니다. 선택지는 두 가지입니다.

1. **CONCEPTS.md 생성(개념 맵 구축)** — 저장소 전체의 개념 맵을 시딩하고 커밋합니다. docs/solutions 분류 단계(Phase 0–4)만 건너뜁니다. `references/concepts-vocabulary.md`를 읽고 그 문서의 **시딩 목표**와 **시딩 범위**(저장소 전체) 규칙을 따릅니다. 선언된 도메인 모델(스키마, 핵심 타입, 주요 모델, 최상위 도메인 문서)에서 저장소 핵심 도메인 명사를 시딩하며, 각 용어는 등록 기준을 충족해야 하고 개수는 코드베이스가 정합니다. 프리앰블(Phase 4.5 참조)을 작성하고, 구성 규칙에 따라 묶은 뒤, `AGENTS.md`/`CLAUDE.md`에서 새 파일을 드러내도록 발견 가능성 검사를 실행합니다. 그 다음 **Phase 5(변경 커밋)**로 들어가 refresh가 사용하는 동일한 영속 쓰기 흐름을 통해 새 `CONCEPTS.md`와 지침 파일 변경을 커밋/PR합니다. 부트스트랩을 커밋하지 않은 채 남겨 두지 않습니다.
2. **Refresh cycle 실행** — 아래의 일반 refresh 흐름을 진행합니다. `CONCEPTS.md`가 없으면 Phase 4.5에서 시딩하고, 이미 있으면 그 단계에서 조정합니다.

Headless 모드에는 질문할 사용자가 없습니다. 기본값은 refresh cycle로 하고(용어는 Phase 4.5에서 시딩 및 조정), 독립적인 저장소 전체 부트스트랩은 실행하지 않았다고 보고서에 기록합니다.

## 상호작용 원칙

**이 원칙은 Interactive 모드에만 적용됩니다. Headless 모드에서는 모든 사용자 질문을 건너뛰고 위 Headless 모드 규칙을 적용합니다.**

`ce-brainstorm`과 같은 상호작용 방식을 따릅니다.

- 질문은 **한 번에 하나씩** 합니다 — 플랫폼의 차단형 질문 도구를 사용합니다. Claude Code에서는 `AskUserQuestion`(스키마가 로드되지 않았다면 먼저 `select:AskUserQuestion`으로 `ToolSearch` 호출), Codex에서는 `request_user_input`, Antigravity CLI(`agy`)에서는 `ask_question`, Pi에서는 `ask_user`(`pi-ask-user` 확장 필요)를 사용합니다. 하네스에 차단형 질문 도구가 없거나 호출에 실패한 경우(예: Codex edit 모드)에만 일반 텍스트로 번호 매긴 선택지로 대체합니다. 스키마 로드가 필요하다는 이유로 대체하지 않습니다. 질문을 조용히 건너뛰지 않습니다.
- 자연스러운 선택지가 있으면 **복수 선택**을 선호합니다.
- **범위와 의도**에서 시작하고, 필요한 경우에만 좁혀 갑니다.
- 근거를 얻기 전에 사용자가 결정을 내리도록 **요청하지 않습니다.**
- 추천을 먼저 제시하고 짧게 설명합니다.

목표는 사용자를 체크리스트에 억지로 통과시키는 것이 아닙니다. 질문을 최소화하면서 좋은 유지보수 결정을 내리도록 돕는 것입니다.

## Refresh 순서

다음 순서로 refresh합니다.

1. 관련된 개별 러닝 문서를 먼저 검토합니다.
2. 어떤 러닝이 유효하게 유지되었고, 업데이트되었고, 통합되었고, 대체되었고, 삭제되었는지 기록합니다.
3. 그런 다음 해당 러닝에 의존하는 패턴 문서를 검토합니다.

이 순서를 따르는 이유:

- 러닝 문서가 일차적인 근거입니다.
- 패턴 문서는 하나 이상의 러닝에서 파생됩니다.
- 오래된 러닝은 패턴이 실제보다 더 유효해 보이게 만들 수 있습니다.

사용자가 패턴 문서로 시작하더라도 우려 사항을 이해하기 위해 먼저 그 문서를 살펴볼 수 있지만, 패턴을 변경하기 전에 지원하는 러닝 문서를 조사합니다.

## 유지보수 모델

각 후보 아티팩트를 다음 다섯 결과 중 하나로 분류합니다.

| 결과 | 의미 | 기본 작업 |
|---------|------|----------------|
| **Keep** | 여전히 정확하고 유용함 | 기본적으로 파일을 편집하지 않고 검토했으며 신뢰할 수 있다고 보고 |
| **Update** | 핵심 해결책은 맞지만 참조가 변경됨 | 근거가 있는 제자리 편집 적용 |
| **Consolidate** | 둘 이상의 문서가 많이 겹치지만 모두 정확함 | 고유 내용을 정본 문서에 병합하고 피통합 문서 삭제 |
| **Replace** | 기존 아티팩트가 이제 오해를 일으키지만 더 나은 대체물이 알려져 있음 | 신뢰할 수 있는 후속 문서를 만들고 기존 문서 삭제 |
| **Delete** | 더 이상 유용하지 않거나, 적용되지 않거나, 독립성이 없음 | 파일 삭제 — 필요한 경우 Git 기록에서 복구 가능 |

## 핵심 규칙

1. **근거가 판단을 이끕니다.** 아래 신호는 입력값이지 기계적인 점수표가 아닙니다. 아티팩트를 계속 신뢰할 수 있는지 공학적 판단으로 결정합니다.
2. **쓰지 않는 Keep을 우선합니다.** 검토 흔적을 남기기 위해 문서를 업데이트하지 않습니다.
3. **현실에 문서를 맞추지, 문서에 현실을 맞추지 않습니다.** 현재 코드가 러닝과 다르면 러닝을 현재 코드에 맞춥니다. 이 스킬의 역할은 문서 정확성이며 코드 리뷰가 아닙니다 — 코드 변경이 "의도된 것"인지 "회귀"인지 사용자에게 묻지 않습니다. 코드가 바뀌었다면 문서가 그에 맞아야 합니다. 사용자가 코드가 잘못되었다고 생각한다면 이는 이 워크플로 밖의 별도 문제입니다.
4. **단호하게 결정하고 질문을 최소화합니다.** 근거가 명확하면(파일 이름 변경, 클래스 이동, 깨진 참조) 업데이트를 적용합니다. Interactive 모드에서는 올바른 작업이 실제로 모호할 때만 사용자에게 묻습니다. Headless 모드에서는 묻는 대신 모호한 경우 stale로 표시합니다. 목표는 모든 발견에 질문하는 것이 아니라, 판단이 필요한 지점에만 사람의 감독을 두는 자동화된 유지보수입니다.
5. **가치가 낮은 변경을 피합니다.** 정확성이나 사용성을 실질적으로 높이지 않는 오타 수정, 문장 다듬기, 외형적 정리를 위해 문서를 편집하지 않습니다.
6. **Update는 의미 있고 근거가 있는 변경에만 사용합니다.** 경로, 모듈 이름, 관련 링크, 카테고리 메타데이터, 코드 조각, 명백히 오래된 표현은 수정으로 정확성이 실질적으로 좋아지는 경우에만 대상이 됩니다.
7. **실제 대체물이 있을 때만 Replace를 사용합니다.** 다음 중 하나여야 합니다.
   - 현재 대화에 최근 해결 및 검증된 대체 수정이 있음
   - 사용자가 후속 문서를 정직하게 작성할 수 있을 만큼 구체적인 대체 컨텍스트를 제공함
   - 코드베이스 조사에서 현재 접근법을 찾아 이를 후속 문서로 설명할 수 있음
   - 최신 문서, 패턴 문서, PR 또는 이슈가 강력한 후속 근거를 제공함
8. **코드가 사라진 경우 인바운드 링크를 확인한 뒤 삭제합니다.** 참조된 코드, 컨트롤러 또는 워크플로가 코드베이스에 더 이상 없고 후속 문서도 찾을 수 없다면 삭제합니다. 일반적인 조언이 여전히 "타당"하다는 이유로 Keep을 기본값으로 삼지 않습니다. Keep과 Delete 사이에서 확신이 없으면 Interactive 모드에서는 사용자에게 묻고 Headless 모드에서는 stale로 표시합니다. 인바운드 링크는 분류에 영향을 주지만 정리는 항상 기계적입니다. **장식적인** 인용(원칙을 본문에 적고 덧붙인 인용)은 Delete를 허용하지만, **실질적인** 인용(인용된 문서에 의존하는 문서)은 Replace 신호입니다. 인용이 없거나 장식적이고, 일치하는 후속 문서도 없을 때 자동 삭제가 가능합니다.
9. **정확성뿐 아니라 문서 세트의 설계도 평가합니다.** 각 문서가 여전히 정확한지 확인하는 것과 함께 지식에 맞는 단위인지 평가합니다. 둘 이상의 문서가 많이 겹치면 계속 분리할지, 범위를 더 명확히 나눌지, 하나의 정본으로 통합할지 결정합니다. 중복 문서는 조용히 드리프트하므로 위험합니다. 같은 내용을 말하는 두 문서는 결국 서로 다른 내용을 말하게 됩니다.
10. **보관하지 말고 삭제합니다.** `_archived/` 디렉터리는 없습니다. 문서가 더 이상 유용하지 않으면 삭제합니다. Git 기록이 아카이브입니다. 전용 아카이브 디렉터리는 쌓이고 검색 결과를 오염시키며 아무도 읽지 않는 문제를 만듭니다. 누군가 삭제된 문서가 필요하면 `git log --diff-filter=D -- docs/solutions/`로 찾을 수 있습니다.

## 범위 선택

먼저 `docs/solutions/` 아래에서 러닝과 패턴 문서를 발견합니다.

제외 항목:

- `README.md`
- `docs/solutions/_archived/`(레거시 — 이 디렉터리가 있으면 보고서에서 정리 대상으로 표시)

`README.md`와 `_archived/` 아래의 항목을 제외하고 `docs/solutions/` 아래의 모든 `.md` 파일을 찾습니다. `_archived/` 디렉터리가 있으면 정리해야 할 레거시 아티팩트로 보고서에 기록합니다(파일을 복원하거나 삭제).

`$ARGUMENTS`가 제공되면 작업을 진행하기 전에 이를 사용해 범위를 좁힙니다. 결과가 나오는 첫 전략에서 멈추며 다음 순서로 시도합니다.

1. **디렉터리 일치** — 인자가 `docs/solutions/` 아래의 하위 디렉터리 이름과 일치하는지 확인합니다(예: `performance-issues`, `database-issues`).
2. **프런트매터 일치** — 러닝 프런트매터의 `module`, `component` 또는 `tags` 필드에서 검색합니다.
3. **파일명 일치** — 파일명과 대조합니다(부분 일치 허용).
4. **콘텐츠 검색** — 인자를 키워드로 문서 내용에서 검색합니다(기능 이름이나 영역에 유용).

일치하는 항목이 없으면 그 사실을 보고하고 사용자에게 명확히 해 달라고 요청합니다. Headless 모드에서 범위 힌트가 제공되었지만 아무것도 일치하지 않으면 전체로 넓히지 말고, 불일치를 보고서에 기록한 뒤 모든 문서 처리를 종료합니다. (Headless 모드의 "모든 문서 처리" 규칙은 범위 힌트가 **없을 때만** 적용됩니다.)

후보 문서가 없으면 다음을 보고합니다.

```text
No candidate docs found in docs/solutions/.
Run `compound` after solving problems to start building your knowledge base.
```

## Phase 0: 평가 및 라우팅

사용자에게 분류를 요청하기 전에 다음을 수행합니다.

1. 후보 아티팩트를 발견합니다.
2. 범위를 추정합니다.
3. 상황에 맞는 가장 가벼운 상호작용 경로를 선택합니다.

### 범위에 따른 라우팅

| 범위 | 사용 시점 | 상호작용 방식 |
|-------|-------------|-------------------|
| **Focused** | 가능성이 높은 파일이 1~2개이거나 사용자가 특정 문서를 지정함 | 직접 조사한 뒤 추천을 제시 |
| **Batch** | 대부분 독립적인 문서가 약 8개 이하 | 먼저 조사한 뒤 묶어서 추천 |
| **Broad** | 문서가 9개 이상이거나 모호하거나 저장소 전체의 오래된 문서를 훑음 | 먼저 분류하고 묶음으로 조사 |

### Broad 범위의 초기 분류

범위가 넓을 때(후보 9개 이상)는 심층 조사 전에 가벼운 분류를 수행합니다.

1. **목록화** — 모든 후보 문서의 프런트매터를 읽고 모듈/컴포넌트/카테고리별로 묶습니다.
2. **영향 클러스터링** — 러닝과 패턴 문서가 가장 밀집된 영역을 찾습니다. 동일 모듈을 다루는 러닝 5개와 패턴 2개가 서로 연결된 클러스터는 고립된 단일 문서 5개보다 영향이 큽니다. 한 문서의 오래됨이 다른 문서에도 영향을 줄 가능성이 크기 때문입니다.
3. **드리프트 표본 검사** — 각 클러스터에서 주요 참조 파일이 여전히 존재하는지 확인합니다. 영향이 큰 클러스터에서 참조 누락이 발견되면 우선 시작할 가장 강한 신호입니다.
4. **시작 영역 추천** — 가장 영향이 큰 클러스터와 간단한 근거를 제시하고 사용자에게 확인 또는 방향 변경을 요청합니다. Headless 모드에서는 질문을 건너뛰고 영향 순서대로 모든 클러스터를 처리합니다.

예:

```text
Found 24 learnings across 5 areas.

The auth module has 5 learnings and 2 pattern docs that cross-reference
each other — and 3 of those reference files that no longer exist.
I'd start there.

1. Start with auth (recommended)
2. Pick a different area
3. Review everything
```

아직 작업 선택 질문을 하지 않습니다. 먼저 근거를 모읍니다.

## Phase 1: 후보 러닝 조사

범위 내 각 러닝을 읽고, 현재 코드베이스의 주장과 대조하고, 추천을 구성합니다.

러닝은 서로 독립적으로 오래될 수 있는 여러 차원이 있습니다. 표면 검사는 명백한 드리프트를 잡지만, 오래됨은 더 깊은 곳에 숨어 있는 경우가 많습니다.

- **참조** — 언급된 파일 경로, 클래스 이름, 모듈이 여전히 존재하는가, 아니면 이동했는가?
- **권장 해결책** — 해결책이 오늘날 코드가 실제로 작동하는 방식과 여전히 일치하는가? 이름이 바뀐 파일이 완전히 다른 구현 패턴을 가진다면 단순한 경로 업데이트가 아닙니다.
- **코드 예시** — 코드 조각이 현재 구현을 여전히 반영하는가?
- **관련 문서** — 상호 참조되는 러닝과 패턴이 여전히 존재하고 일관적인가?
- **Auto memory**(Claude Code만) — 시스템 프롬프트에 주입된 auto-memory 블록에 같은 문제 영역의 항목이 있는가? 그 블록을 직접 확인합니다. 블록이 없으면 이 차원은 건너뜁니다. 러닝과 다른 접근법을 설명하는 메모는 보조적인 드리프트 신호입니다.
- **겹침** — 조사 중 다른 범위 내 문서가 같은 문제 영역을 다루거나, 같은 파일을 참조하거나, 비슷한 해결책을 권장하는지 기록합니다. 각 겹침에 대해 두 파일 경로, 겹치는 차원(문제, 해결책, 근본 원인, 파일, 예방), 더 포괄적이거나 최신인 문서를 기록합니다. 이 신호는 Phase 1.75(문서 세트 분석)의 입력입니다.
- **용어** — 러닝이 인용하는 도메인 용어(엔티티, 이름이 붙은 프로세스, 프로젝트 고유 의미의 상태 개념)를 기록합니다. `CONCEPTS.md`에 있는지, 있다면 정의가 코드의 사용 방식과 여전히 일치하는지 확인합니다. 없다면 Phase 4.5에서 추가 또는 부트스트랩할 용어로 표시합니다. 조사 중에는 `CONCEPTS.md`를 편집하지 말고 신호를 중앙에 모읍니다.

조사의 깊이는 러닝의 구체성에 맞춥니다. 정확한 파일 경로와 코드 조각을 언급하는 러닝은 일반 원칙을 설명하는 러닝보다 더 많이 검증해야 합니다.

### 드리프트 분류: Update와 Replace

핵심 구분은 드리프트가 **외형적**인지(참조는 이동했지만 해결책은 동일) 아니면 **실질적**인지(해결책 자체가 바뀜)입니다.

- **Update 영역** — 파일 경로가 이동하고, 클래스 이름이 바뀌고, 링크가 깨지고, 메타데이터가 바뀌었지만 핵심 권장 접근법은 여전히 코드가 작동하는 방식인 경우입니다. `compound-refresh`가 이를 직접 수정합니다.
- **Replace 영역** — 권장 해결책이 현재 코드와 충돌하거나, 아키텍처 접근법이 바뀌었거나, 패턴이 더 이상 선호되지 않는 경우입니다. 새 러닝을 작성해야 합니다. 대체 서브에이전트가 이미 수집된 조사 근거를 사용해 `compound` 문서 형식(프런트매터, 문제, 근본 원인, 해결책, 예방)에 따라 후속 문서를 작성합니다. 오케스트레이터는 러닝을 인라인으로 다시 작성하지 않고 컨텍스트 격리를 위해 서브에이전트에 위임합니다.

**경계:** 해결책 섹션을 다시 쓰거나 러닝이 권장하는 내용을 바꾸고 있다면 멈춥니다 — 이는 Update가 아니라 Replace입니다.

**메모리에서 유래한 드리프트 신호**는 보조적이며 일차적인 근거가 아닙니다. 코드베이스의 뒷받침이 없는 다른 접근법을 말하는 메모리만으로 Replace나 Delete를 정당화하지 않습니다. 메모리 신호는 다음에 사용합니다.
- 코드베이스에서 얻은 드리프트를 뒷받침(Replace 근거 강화)
- 코드베이스의 근거가 경계선일 때 더 깊은 조사를 촉발
- 근거 보고서에 컨텍스트 추가("(auto memory [claude])는 이 러닝이 작성된 이후 접근법 X가 바뀌었을 수 있음을 시사함")

Headless 모드에서는 메모리만의 드리프트(코드베이스 뒷받침 없음)는 작업이 아니라 stale 표시로 처리합니다.

### 판단 지침

쉽게 잘못 적용하는 지침 세 가지:

1. **모순은 강한 Replace 신호입니다.** 러닝의 권장이 현재 코드 패턴 또는 최근 검증된 수정과 충돌하면 사소한 드리프트가 아니라 적극적으로 오해를 일으키는 상태입니다. Replace로 분류합니다.
2. **나이만으로는 오래된 신호가 아닙니다.** 2년 된 러닝도 현재 코드와 일치하고 유용하다면 괜찮습니다. 나이는 더 주의 깊게 조사하게 하는 신호로만 사용합니다.
3. **삭제 전에 후속 문서를 확인합니다.** Replace나 Delete를 권장하기 전에 같은 문제 공간을 다루는 최신 러닝, 패턴 문서, PR 또는 이슈를 찾습니다. 후속 근거가 있으면 Delete보다 Replace를 우선해 독자가 새 지침을 찾도록 합니다.

## Phase 1.5: 패턴 문서 조사

기반이 되는 러닝 문서를 검토한 뒤 `docs/solutions/patterns/` 아래의 관련 패턴 문서를 조사합니다.

패턴 문서는 영향력이 큽니다. 오래된 패턴은 향후 작업에서 광범위하게 적용될 수 있으므로 개별 러닝보다 더 위험합니다. 갱신된 러닝의 상태를 고려할 때 일반화된 규칙이 여전히 성립하는지 평가합니다.

명확한 지원 러닝이 없는 패턴 문서는 오래됨의 신호입니다. 변경 없이 유지하기 전에 주의 깊게 조사합니다.

## Phase 1.75: 문서 세트 분석

개별 문서를 조사한 뒤 한 걸음 물러서서 전체 문서 세트를 평가합니다. 목표는 현실과 비교했을 때뿐 아니라 문서끼리 비교했을 때만 보이는 문제를 찾는 것입니다.

### 겹침 탐지

같은 모듈, 컴포넌트, 태그 또는 문제 영역을 공유하는 문서는 다음 차원으로 비교합니다.

- **문제 서술** — 같은 근본 문제를 설명하는가?
- **해결책 형태** — 표현이 달라도 같은 접근법을 권장하는가?
- **참조 파일** — 같은 코드 경로를 가리키는가?
- **예방 규칙** — 같은 예방 불릿을 반복하는가?
- **근본 원인** — 같은 근본 원인을 식별하는가?

3개 이상의 차원에서 겹치면 강한 Consolidate 신호입니다. 던질 질문은 다음과 같습니다. "향후 유지보수자가 현재의 진실을 얻기 위해 두 문서를 모두 읽어야 하는가, 아니면 한 문서가 다른 문서를 대부분 반복하는가?"

### Supersession 신호

"더 오래된 좁은 선행 문서, 더 최신인 정본 문서" 패턴을 찾습니다.

- 더 최신 문서가 같은 파일과 워크플로를 다루면서 더 넓은 런타임 동작까지 포함함
- 더 오래된 문서가 특정 사건을 설명하고 더 최신 문서가 이를 패턴으로 일반화함
- 두 문서가 같은 수정을 권장하지만 더 최신 문서가 더 나은 컨텍스트, 예시 또는 범위를 제공함

더 최신 문서가 더 오래된 문서를 명확히 포괄하면, 더 오래된 문서는 통합 후보입니다. 고유 내용이 있다면 더 최신 문서에 병합하고, 더 오래된 문서는 삭제합니다.

### 정본 문서 식별

문제 영역을 공유하는 각 주제 클러스터에서 **정본(진실의 원천)** 문서를 식별합니다.

- 보통 클러스터에서 가장 최신이고 포괄적이며 정확한 문서
- 유지보수자가 이 주제를 검색할 때 가장 먼저 찾아야 하는 문서
- 다른 문서가 중복해서 가리키는 대신 가리켜야 하는 문서

클러스터의 나머지 문서는 다음 중 하나입니다.
- **Distinct** — 의미 있게 다른 하위 문제를 다루고 독립적인 검색 가치가 있음. 계속 분리해 둡니다.
- **Subsumed** — 고유 내용이 정본 문서의 섹션으로 들어갈 수 있음. 통합합니다.
- **Redundant** — 정본 문서가 이미 말하는 것 외에 아무것도 더하지 않음. 삭제합니다.

### 검색 가치 테스트

두 문서를 계속 분리해 두기 전에 다음을 묻습니다. "6개월 후 유지보수자가 이 주제를 검색한다면, 문서가 분리되어 있는 것이 검색 가능성을 높이는가, 아니면 드리프트 위험만 키우는가?"

다음 조건에서만 문서를 분리해 둘 가치가 있습니다.
- 누군가 독립적으로 검색할 법한, 진정으로 다른 하위 문제를 다룸
- 서로 다른 대상이나 컨텍스트를 겨냥함(예: 하나는 디버깅, 다른 하나는 예방)
- 병합하면 드리프트 위험보다 탐색을 더 어렵게 만드는 지나치게 큰 문서가 됨

어느 조건도 해당하지 않으면 통합을 우선합니다. 같은 내용을 다루는 두 문서는 결국 서로 어긋나고 모순됩니다. 이는 약간 더 긴 단일 문서보다 나쁩니다.

### 문서 간 충돌 검사

범위 내 문서 간의 명백한 모순을 찾습니다.
- 문서 A는 "항상 접근법 X를 사용하라"고 하고 문서 B는 "접근법 X를 피하라"고 함
- 문서 A는 문서 B가 폐기했다고 말한 파일 경로를 참조함
- 문서 A와 문서 B가 같은 문제로 보이는 것에 대해 서로 다른 근본 원인을 설명함

문서 간 모순은 개별적인 오래됨보다 긴급합니다. 독자를 적극적으로 혼란스럽게 하기 때문입니다. 하나가 같은 진실의 오래된 버전이고 다른 하나가 맞다면 Consolidate로 즉시 해결하고, 그 외에는 대상 Update/Replace로 해결하도록 표시합니다.

## 서브에이전트 전략

여러 아티팩트를 조사할 때 컨텍스트 격리를 위해 서브에이전트를 사용합니다 — 작업이 복잡해 보인다는 이유만으로 사용하지 않습니다. 상황에 맞는 가장 가벼운 접근법을 선택합니다.

| 접근법 | 사용 시점 |
|----------|-------------|
| **메인 스레드만** | 범위가 작고 문서가 짧음 |
| **순차 서브에이전트** | 지원 파일을 많이 읽어야 하는 아티팩트가 1~2개 |
| **병렬 서브에이전트** | 서로 독립적이고 겹침이 적은 아티팩트가 3개 이상 |
| **배치 서브에이전트** | 넓은 범위 — 먼저 범위를 좁힌 다음 묶음으로 조사 |

**서브에이전트를 생성할 때는** `mode` 파라미터를 생략하여 사용자가 설정한 권한을 적용합니다. 작업 프롬프트에 다음 지침을 포함합니다.

> 조사에는 전용 파일 검색 및 읽기 도구(Glob, Grep, Read)를 사용합니다. 파일 작업에 셸 명령(ls, find, cat, grep, test, bash)을 사용하지 마세요. 이는 권한 요청을 피하고 더 안정적입니다.
>
> 또한 시스템 프롬프트에 주입된 "사용자의 auto-memory" 블록(Claude Code만)을 검사하세요. 러닝의 문제 영역과 관련된 메모를 확인하세요. 메모리에서 유래한 드리프트 신호는 코드베이스에서 유래한 근거와 별도로 보고하고, 근거 섹션에서 "(auto memory [claude])" 태그를 붙이세요. 컨텍스트에 블록이 없으면 이 검사를 건너뛰세요.

서브에이전트 역할은 두 가지입니다.

1. **조사 서브에이전트** — 읽기 전용입니다. 파일을 편집하거나 후속 문서를 만들거나 삭제해서는 안 됩니다. 각각 파일 경로, 근거, 권장 작업, 확신도, 열린 질문을 반환합니다. 아티팩트가 독립적이면 병렬로 실행할 수 있습니다.
2. **대체 서브에이전트** — stale 러닝 하나를 대체할 새 러닝 하나를 작성합니다. 이들은 순차적으로 하나씩 실행합니다(각 대체 서브에이전트가 상당한 코드를 읽어야 할 수 있고, 여러 개를 병렬로 실행하면 컨텍스트가 소진될 위험이 있기 때문입니다). 각 대체가 완료된 후 모든 삭제 및 메타데이터 업데이트는 오케스트레이터가 처리합니다.

오케스트레이터는 조사 결과를 합치고, 모순을 찾고, 대체 서브에이전트를 조정하고, 모든 삭제/메타데이터 편집을 중앙에서 수행합니다. Interactive 모드에서는 모호한 경우 사용자에게 질문하고, Headless 모드에서는 대신 stale로 표시합니다. 두 아티팩트가 겹치거나 같은 근본 문제를 다루면 병렬화하지 말고 함께 조사합니다.

## Phase 2: 올바른 유지보수 작업 분류

근거를 수집한 뒤 권장 작업을 하나 지정합니다.

### Keep

러닝이 여전히 정확하고 유용합니다. 파일을 편집하지 않고 검토했으며 신뢰할 수 있다고 보고합니다. 다른 이유로 의미 있는 업데이트를 이미 하고 있을 때만 `last_refreshed`를 추가합니다.

### Update

핵심 해결책은 유효하지만 참조(경로, 클래스 이름, 링크, 코드 조각, 메타데이터)가 변경되었습니다. 수정 사항을 직접 적용합니다.

### Consolidate

Phase 1.75에서 문서가 많이 겹치지만 모두 실질적으로 정확하다고 확인했을 때 **Consolidate**를 선택합니다. 이는 한 문서의 드리프트를 고치는 Update, 오해를 일으키는 지침을 다시 쓰는 Replace와 다릅니다. Consolidate는 "둘 다 맞지만 하나가 다른 하나를 포괄한다"는 경우를 처리합니다.

**통합할 때:**

- 두 문서가 같은 문제를 설명하고 같거나 호환되는 해결책을 권장함
- 하나는 좁은 선행 문서이고 최신 문서가 같은 내용을 더 넓게 다룸
- 피통합 문서의 고유 내용이 정본 문서의 섹션 또는 부록으로 들어갈 수 있음
- 둘을 모두 유지하면 의미 있는 검색 이점 없이 드리프트 위험이 생김

**통합하지 않을 때**(Phase 1.75의 검색 가치 테스트 적용):

- 누군가 독립적으로 검색할, 진정으로 다른 하위 문제를 다룸
- 병합하면 드리프트 위험보다 탐색을 더 해치는 지나치게 큰 문서가 됨

Consolidate 작업은 피통합 문서의 고유 내용을 정본 문서에 병합한 뒤 피통합 문서를 삭제하는 것입니다. 보관하지 않고 삭제합니다. Git 기록이 보존합니다.

**Consolidate와 Delete의 구분:** 피통합 문서에 보존할 가치가 있는 고유 내용(엣지 케이스, 다른 접근법, 추가 예방 규칙)이 있으면 먼저 Consolidate로 병합합니다. 정본 문서가 이미 말하는 것 외에는 아무것도 더하지 않으면 바로 Delete로 넘어갑니다.

### Replace

핵심 지침이 이제 오해를 일으킬 때 **Replace**를 선택합니다 — 권장 수정이 실질적으로 바뀌었거나, 근본 원인 또는 아키텍처가 달라졌거나, 선호되는 패턴이 달라진 경우입니다.

사용자가 기존 러닝을 작성한 지 수개월 후에 refresh를 실행할 수 있습니다. 사용자가 제공하기 어려운 대체 컨텍스트를 요청하지 말고, 에이전트의 지능으로 코드베이스를 조사하고 대체 문서를 종합합니다.

**근거 평가:**

Replace 후보를 식별할 때쯤이면 Phase 1 조사에서 이미 상당한 근거를 모았습니다. 기존 러닝의 주장, 현재 코드가 실제로 하는 일, 드리프트가 발생한 지점을 파악한 상태입니다. 이 근거가 신뢰할 수 있는 후속 문서를 작성하기에 충분한지 평가합니다.

- **근거 충분** — 기존 러닝이 권장한 것과 현재 접근법을 모두 이해합니다. 현재 코드 패턴, 새 파일 위치, 변경된 아키텍처를 조사했습니다. → 후속 문서를 작성합니다(Phase 4 Replace 흐름 참조).
- **근거 부족** — 드리프트가 너무 근본적이어서 현재 접근법을 자신 있게 문서화할 수 없습니다. 하위 시스템 전체가 교체되었거나 새 아키텍처가 파일 검색만으로 이해하기에 너무 복잡합니다. → 제자리에서 stale로 표시합니다.
  - 프런트매터에 `status: stale`, `stale_reason: [what you found]`, `stale_date: YYYY-MM-DD`를 추가합니다.
  - 발견한 근거와 부족한 근거를 보고합니다.
  - 사용자가 해당 문제 영역을 다음에 만났을 때 최신 문제 해결 컨텍스트를 가지고 `compound`를 실행하도록 권장합니다.

### Delete

다음과 같은 경우 **Delete**를 선택합니다.

- 코드 또는 워크플로가 더 이상 존재하지 않고 문제 영역도 사라짐
- 러닝이 더 이상 유효하지 않고 문서화할 가치가 있는 최신 대체물도 없음
- 러닝이 다른 문서와 완전히 중복됨(먼저 병합할 고유 내용이 있으면 Consolidate 사용)
- Replace로 대체해야 한다는 의미 있는 후속 근거가 없음

작업: 파일을 삭제합니다. 아카이브 디렉터리도, 메타데이터도 두지 않습니다. 복구가 필요하면 Git 기록에서 삭제된 파일을 찾을 수 있습니다.

### 삭제 전: 문제 영역이 여전히 활성 상태인지 확인

러닝이 참조하는 파일이 사라진 것은 강한 근거지만 **구현**이 사라졌다는 뜻일 뿐입니다. 삭제하기 전에 러닝이 해결하는 **문제**가 코드베이스에서 여전히 관심사인지 판단합니다.

- `auth_token.rb`가 없어도 세션 토큰을 처리하는 애플리케이션이라면, 개념은 새 구현 아래에 남아 있습니다. 이는 Delete가 아니라 Replace입니다.
- 더 이상 사용되지 않는 API 엔드포인트의 문서를 다루며 기능 전체가 제거되었다면 문제 영역도 사라진 것입니다. 이는 Delete입니다.

기존 러닝의 키워드를 기계적으로 검색하지 않습니다. 러닝이 다루는 문제를 이해한 뒤 그 문제가 현재 코드베이스에서 여전히 존재하는지 조사합니다. 에이전트는 개념을 이해하므로, 예전 코드가 있던 곳이 아니라 현재 문제가 살아 있는 위치를 찾아야 합니다.

### 삭제 전: 인바운드 링크 확인

다른 파일이 인용하는 문서는 문서 자체가 알리는 것보다 더 중요한 역할을 합니다. Delete로 분류하기 전에 저장소의 Markdown 콘텐츠(다른 문서, 계획, 지침 파일, README)에서 해당 파일을 인용하는지 검색합니다. 인용은 드물고 주석에만 나타나는 소스 코드는 검색 대상이 아닙니다. 파일명 slug는 대개 고유하므로 한 번의 검색으로 모든 인용 위치를 찾을 수 있습니다.

효율적으로 검색합니다.

- 셸보다 플랫폼의 기본 콘텐츠 검색 도구(예: Claude Code의 Grep)를 우선합니다. 해당 사례에서 실질적으로 더 나을 때만 셸을 사용합니다.
- 파일명 slug(`.md` 제외)를 검색하고, 일치가 너무 많을 때만 전체 경로로 좁힙니다.
- 전체 파일 대신 각 일치 항목 주변의 컨텍스트 줄을 읽습니다(예: Grep의 `-B`/`-A`).

**인바운드 링크는 분류에 영향을 주지만 정리 방법은 정하지 않습니다.** 인용을 제거하는 일은 항상 기계적입니다(괄호 속 문구, 단독 항목 또는 위임 절을 제거). 판단은 그보다 앞선 단계에서 합니다. 이 인용을 고려할 때 Delete가 여전히 맞는지, Replace가 더 가까운지 판단합니다.

각 인용을 인용하는 맥락에 따라 분류합니다.

- **장식적** — 원칙이 본문에 인라인으로 있고, 인용은 "관련 문서" 포인터나 단순한 출처 표시임. Delete해도 괜찮으며 같은 커밋에서 인용을 정리합니다.
- **실질적** — 인용하는 문서가 본문에 없는 내용을 인용된 문서에 의존함(예: 인라인 설명 없이 "Y에 대한 자세한 내용은 X 참조"). Replace 신호입니다. 같은 경로에 후속 문서를 작성하거나, 실제 내용이 제목이 암시하는 것보다 넓다면 **범위를 좁힌 Keep**을 선택합니다.
- **혼합 또는 불명확** — stale로 표시합니다.

Headless 모드에서는 Delete와 장식적 인용 정리는 괜찮습니다. 실질적인 인용 또는 진정한 모호성이 하나라도 있으면 stale 표시로 낮춥니다. 후속 문서를 작성하는 일은 판단이 많이 필요하므로 unattended로 수행하지 않습니다.

**자동 삭제는 다음 세 조건을 모두 충족할 때만 가능합니다.**

- 구현이 사라졌거나(또는 명백히 더 나은 후속 문서로 완전히 대체되었거나, 문서가 명백히 중복됨)
- 문제 영역이 사라졌고 — 애플리케이션이 러닝이 다루는 대상을 더 이상 처리하지 않음
- 인바운드 링크가 없거나 명백히 장식적임

어떤 조건이라도 충족하지 않으면 위 규칙에 따라 Replace, Update, Consolidate 또는 stale 표시로 분류합니다. 문제 영역이 여전히 활성 상태이거나 실질적으로 인용되는 러닝은 삭제하지 말고, 대신 후속 문서로 공백을 채웁니다.

## 패턴 지침

패턴 문서에도 동일한 다섯 결과(Keep, Update, Consolidate, Replace, Delete)를 적용하지만, 사건 수준의 러닝이 아니라 **파생 지침**으로 평가합니다. 주요 차이는 다음과 같습니다.

- **Keep**: 기반 러닝이 일반화된 규칙을 계속 뒷받침하고 예시가 여전히 대표성을 가짐
- **Update**: 규칙은 유지되지만 예시, 링크, 범위 또는 지원 참조가 변경됨
- **Consolidate**: 두 패턴 문서가 같은 러닝 집합을 일반화하거나 같은 설계 관심사를 다룸 — 하나의 정본 패턴으로 병합
- **Replace**: 일반화된 규칙이 이제 오해를 일으키거나 기반 러닝이 다른 종합을 뒷받침함. 갱신된 러닝 세트를 근거로 후속 문서를 만들며 추측으로 새 규칙을 만들지 않음
- **Delete**: 패턴이 더 이상 유효하지 않거나 반복되지 않거나, 고유 내용이 남지 않은 채 더 강한 패턴 문서에 완전히 흡수됨

## Phase 3: 결정 질문

### Headless 모드

**이 전체 단계를 건너뜁니다. 질문하지 않고, 선택지를 제시하지 않고, 입력을 기다리지 않습니다.** Phase 2의 분류에 따라 바로 Phase 4로 진행하고 모든 작업을 실행합니다.

- 모호하지 않은 Keep, Update, Consolidate, 자동 Delete 및 (근거가 충분한) Replace → 바로 실행
- 모호한 경우 → stale로 표시
- 그런 다음 보고서를 생성합니다(출력 형식 참조).

### Interactive 모드

대부분의 Update와 Consolidate는 질문 없이 바로 적용합니다. 다음 경우에만 사용자에게 묻습니다.

- 올바른 작업이 실제로 모호함(Update와 Replace, Consolidate와 Delete의 구분)
- 문서를 Delete하려 하지만 근거가 명백하지 않음(Phase 2의 자동 삭제 기준 참조). 자동 삭제 기준이 충족되면 묻지 않고 진행
- Consolidate하려 하지만 정본 문서를 명확하게 선택할 수 없음
- Replace로 후속 문서를 만들 예정임

코드 변경이 의도된 것인지, 사용자가 코드의 버그를 고치고 싶은지, 문서 유지보수 밖의 문제를 묻지 않습니다. 맡은 범위를 지킵니다.

#### 질문 방식

항상 플랫폼의 차단형 질문 도구로 선택지를 제시합니다. Claude Code에서는 `AskUserQuestion`(스키마가 로드되지 않았다면 먼저 `select:AskUserQuestion`으로 `ToolSearch` 호출), Codex에서는 `request_user_input`, Antigravity CLI(`agy`)에서는 `ask_question`, Pi에서는 `ask_user`(`pi-ask-user` 확장 필요)를 사용합니다. 하네스에 차단형 질문 도구가 없거나 호출에 실패한 경우(예: Codex edit 모드)에만 일반 텍스트로 번호 매긴 선택지를 제시합니다. 스키마 로드가 필요하다는 이유로 대체하지 않습니다. 질문을 조용히 건너뛰지 않습니다.

질문 규칙:

- **한 번에 하나씩** 질문
- **복수 선택** 선호
- **추천 옵션을 먼저** 제시
- 근거에 기반한 이유를 한 문장으로 간단히 설명
- 실제로 가능한 작업이 아닌 항목을 선택지에 넣지 않음

#### Focused 범위

단일 아티팩트에 대해서는 다음을 제시합니다.

- 파일 경로
- 근거 2~4개
- 권장 작업

그런 다음 다음과 같이 질문합니다.

```text
This [learning/pattern] looks like a [Keep/Update/Consolidate/Replace/Delete].

Why: [one-sentence rationale based on the evidence]

What would you like to do?

1. [Recommended action]
2. [Second plausible action]
3. Skip for now
```

다섯 작업을 모두 제시할 필요는 없습니다. 다섯 가지가 모두 실제로 가능한 경우에만 모두 나열합니다.

#### Batch 범위

여러 러닝에 대해서는 다음과 같이 합니다.

1. 명백한 **Keep** 사례를 함께 묶습니다.
2. 수정이 단순한 명백한 **Update** 사례를 함께 묶습니다.
3. 정본 문서가 명확한 **Consolidate** 사례를 함께 제시합니다.
4. **Replace** 사례는 개별적으로 또는 아주 작은 그룹으로 제시합니다.
5. **Delete** 사례는 자동 삭제 후보로 확실한 경우를 제외하고 개별적으로 제시합니다.

확인은 단계적으로 요청합니다.

1. 묶은 Keep/Update 권장 사항 확인
2. 그 다음 Consolidate 그룹 처리(정본 문서와 병합할 내용 제시)
3. Replace를 한 번에 하나씩 처리
4. 자동 적용하기에 명백하고 안전한 삭제가 아니라면 Delete를 한 번에 하나씩 처리

#### Broad 범위

사용자가 전면적인 refresh를 요청했다면 상호작용을 점진적으로 유지합니다.

1. 먼저 범위를 좁힙니다.
2. 관리 가능한 묶음을 조사합니다.
3. 추천을 제시합니다.
4. 다음 묶음으로 계속할지 묻습니다.

전체 유지보수 큐를 사용자에게 한꺼번에 제시하지 않습니다.

## Phase 4: 선택한 작업 실행

각 후보에 대해 Phase 2에서 분류하고 Phase 3에서 확정한 작업에 맞는 흐름을 실행합니다. `references/per-action-flows.md`를 읽고 해당 섹션을 따릅니다.

- **Keep** — 기본적으로 파일을 편집하지 않고, 러닝이 신뢰할 수 있는 이유를 요약합니다.
- **Update** — 해결책이 여전히 실질적으로 올바를 때 제자리에서 편집합니다(경로 이름 변경, 링크 갱신, 모듈 이름 변경).
- **Consolidate** — 겹치는 문서를 정본 문서에 병합하고, 피통합 문서를 삭제하고, 상호 참조를 업데이트합니다. 오케스트레이터가 직접 통합을 처리합니다.
- **Replace** — 지원 문서를 전달해 서브에이전트가 후속 러닝을 작성하고, 프런트매터 및 인용된 주장 검사를 실행한 뒤 기존 문서를 삭제합니다. 근거가 부족하면 stale로 표시합니다.
- **Delete** — 최종 인바운드 링크 검사를 실행한 뒤 제거합니다. 늦게 실질적인 인용이 발견되면 재분류합니다.

후보마다 하나의 흐름만 실행합니다. 참조 문서에 각 기준, 예시 및 단계별 지침이 있습니다.

## Phase 4.5: 용어 포착

문서별 작업이 실행된 뒤 Phase 1의 Vocabulary 차원에서 표시한 도메인 용어를 모아 `CONCEPTS.md`와 조정합니다.

**먼저 `references/concepts-vocabulary.md`를 읽습니다.** 이는 무조건 수행합니다. Phase 1 신호 중 어떤 것이 조건을 충족하는지 기억으로 미리 판단하지 않습니다. 참조 문서의 기준은 쉽게 알 수 없는 것이며, 읽지 않고 "조건을 충족하는 것이 없음"이라고 판단하는 것은 지름길이지 결과가 아닙니다.

**절차:**

1. **집계.** 범위 내 러닝에서 드러난 용어 중 참조 문서의 기준을 적용해 조건을 충족하는 용어를 모읍니다. 같은 용어가 여러 러닝에서 서로 다른 정확성의 관점으로 나타났다면 **하나의 항목으로 관점을 합칩니다** — 세 항목으로 나누지 말고, 최신 항목 하나만 선택하지도 않습니다.
2. **`CONCEPTS.md`가 있으면**, 없는 용어를 추가하고 코퍼스에서 새로운 정밀성이 드러난 기존 항목을 다듬습니다. 이미 있는 항목은 중복하지 않습니다. **그 다음 범위 내 핵심 명사를 조정합니다:** 참조 문서의 **시딩 목표**에 따라 범위 영역의 선언된 모델에서 핵심 도메인 명사를 다시 도출하고, 중심적이지만 빠진 용어를 보완합니다. 이는 마찰이 드러내지 않는 안정적이고 중심적인 용어를 위한 매 실행 안전망입니다. 범위 내 영역으로 제한하고, 이번 실행에서 조사한 용어만 정의하며, 저장소 전체를 훑지 않습니다.
3. **`CONCEPTS.md`가 없고 조건을 충족하는 용어가 하나라도 있으면**, 파일을 부트스트랩합니다 — **단일 용어를 쓰지 말고 시딩합니다.** 포착된 용어와 함께 범위 영역의 핵심 도메인 명사를 참조 문서의 **시딩 목표**에 따라 시딩하여, 파일이 주변부 항목 하나가 아니라 기반에서 시작하도록 합니다(포착된 용어가 정의되지 않은 형제 용어에 매달리지 않게 함). 시딩은 범위 영역에 한정합니다 — 저장소 전체 개념 맵은 위의 명시적 부트스트랩 경로로만 만들며 범위가 지정된 refresh가 대신하지 않습니다. **처음 생성할 때는** 경계선 용어에 대해 등록 기준을 보수적으로 적용합니다 — 경계선 용어나 엔티티로 포장한 클래스/테이블/파일 이름은 다음 실행으로 미루고, 분명한 핵심 명사만 시딩합니다. 보수성은 개수가 아니라 품질에 관한 것이며, 이미 있는 파일의 업데이트에는 일반 기준을 적용합니다.
4. **범위 규율과 인용 위생.** 부트스트랩, 시딩, 조정은 범위 내 영역만 반영합니다 — 다른 카테고리로 넓히지 말고, 기존 러닝에 `(see CONCEPTS.md)` 포인터를 소급해 넣지도 않습니다. (위의 저장소 전체 부트스트랩 경로는 의도적으로 선언된 모델 전체를 다루는 예외입니다.) 다른 범위의 refresh 실행에서 추가 항목이 생길 가능성이 있다는 점을 보고서에 적습니다.
5. **초기 구조.** 부트스트랩할 때 `# Concepts` 제목 아래에 다음 프리앰블을 넣고 파일을 시작합니다.

   > Shared domain vocabulary for this project — entities, named processes, and status concepts with project-specific meaning. Seeded with core domain vocabulary, then accretes as compound and compound-refresh process learnings; direct edits are fine. Glossary only, not a spec or catch-all.

   그런 다음 항목을 추가합니다. 용어 수에 따라 형태를 정합니다. 1~4개 용어면 평면 제목, 그보다 많으면 `references/concepts-vocabulary.md`의 규칙에 따라 도메인 관계별로 묶습니다.
6. **위반을 정리합니다.** 기존 항목을 `references/concepts-vocabulary.md` 기준에 어긋나는 내용이 있는지 검사합니다 — 구현 세부사항(파일 경로, 클래스 이름, 함수 시그니처, 코드 참조), 현재 설정값(드리프트할 임계값, 개수, enum 값), 상태/담당자/날짜 메타데이터, 다른 이름으로 이미 다루는 용어의 중복, 정의되지 않은 프로젝트 고유 형제 용어에 의존하는 항목(형제를 추가하거나 다시 표현). 수정하거나 통합합니다. refresh는 감사 작업이므로 전체 점검이 적절합니다. `compound`의 같은 이름 단계는 다루는 항목의 일관성 주변만 수정합니다.

Phase 1 신호를 참조 문서의 기준에 적용한 뒤 조건을 충족하는 것이 없다면 보고서의 `CONCEPTS.md` 줄에 그 결과를 명시합니다(예: "scanned, no qualifying terms"). 조용히 건너뛰지 않습니다 — 검색하고 결과가 없다는 명시적인 기록 자체가 참조 문서를 확인했다는 감사 신호입니다.

참고: 이 실행에서 `CONCEPTS.md`를 **처음 생성**하면 아래 발견 가능성 검사에서도 파일이 드러납니다. Interactive 모드에서는 동의를 받아 `AGENTS.md`/`CLAUDE.md`를 편집하고, Headless 모드에서는 지침 파일을 편집하지 않고 보고서에 "발견 가능성 권장 사항" 줄을 출력합니다(4c 단계의 Headless 경계에 따라 Headless는 문서 유지보수만 수행하고 프로젝트 설정은 변경하지 않음). 어느 경우든 생성된 파일이 노출되거나 노출 권장 사항으로 표시됩니다. 이후 실행에서는 지침 파일이 최신이거나 권장 사항이 이미 보고되었으므로 이 단계를 건너뜁니다.

**모든 모드에서 편집을 조용히 적용합니다 — 사용자에게 묻지 않습니다.** 용어 포착은 refresh의 부수 효과이지 실행마다 사용자가 결정하는 일이 아닙니다.

## 출력 형식

**전체 보고서는 반드시 Markdown 출력으로 인쇄해야 합니다.** 조사 결과를 내부적으로 요약한 뒤 한 줄만 출력하지 않습니다. 보고서가 결과물입니다 — 모든 섹션을 제목, 표, 불릿을 사용해 읽기 쉬운 Markdown으로 완전하게 출력합니다.

선택한 범위를 처리한 뒤 다음 보고서를 출력합니다.

```text
Compound Refresh Summary
========================
Scanned: N learnings

Kept: X
Updated: Y
Consolidated: C
Replaced: Z
Deleted: W
Skipped: V
Marked stale: S

CONCEPTS.md: <scanned, no qualifying terms | created with N entries (M seeded) | updated — N added, N refined, N reconciled, N scrubbed | repo-wide map created with N entries>
```

처리한 **모든** 파일에 대해 다음을 나열합니다.
- 파일 경로
- 분류(Keep/Update/Consolidate/Replace/Delete/Stale)
- 발견한 근거 — 메모리에서 유래한 결과는 코드베이스에서 유래한 근거와 구분되도록 "(auto memory [claude])"를 붙임
- 취한 작업(또는 권장 작업)
- Consolidate인 경우: 어떤 문서가 정본인지, 어떤 고유 내용이 병합되었는지, 무엇을 삭제했는지

**Keep** 결과는 변경 없이 검토한 섹션에 나열하여 결과가 보이도록 합니다. Git 변경을 만들기 위한 편집은 하지 않습니다.

### Headless 모드 보고서

Headless 모드에서는 보고서가 유일한 결과물입니다 — 후속 질문을 할 사용자가 없으므로 보고서는 자체적으로 완전해야 합니다. **전체 보고서를 출력합니다. 축약하거나 요약하거나 섹션을 건너뛰지 않습니다.**

작업을 두 섹션으로 나눕니다.

**Applied**(성공한 쓰기):
- 각 **Updated** 파일: 수정한 참조와 그 이유
- 각 **Consolidated** 클러스터: 정본 문서, 각 피통합 문서에서 병합한 고유 내용, 삭제한 피통합 문서
- 각 **Replaced** 파일: 기존 러닝이 권장한 내용과 현재 코드의 차이, 새 후속 문서의 경로
- 각 **Deleted** 파일: 파일 경로와 제거 이유(문제 영역 소멸, 완전한 중복 등)
- 각 **Marked stale** 파일: 발견한 근거와 모호한 이유

**Recommended**(권한 거부 등으로 기록하지 못한 작업):
- 위와 동일한 상세 내용을 사람이 적용할 권장 사항으로 표현
- 사용자가 직접 변경하거나 Interactive 모드로 스킬을 다시 실행할 수 있을 만큼 충분한 컨텍스트 포함

모든 쓰기에 성공하면 Recommended 섹션은 비어 있습니다. 쓰기에 하나도 성공하지 못했다면(예: 읽기 전용 실행) 모든 작업이 Recommended에 들어가며 보고서는 유지보수 계획이 됩니다.

**레거시 정리**(`docs/solutions/_archived/`가 있는 경우):
- 발견한 아카이브 파일과 처분 권장 사항을 나열합니다: 여전히 관련 있으면 복원, 완전히 오래되었으면 삭제, 활성 문서와 겹치면 통합

## Phase 5: 변경 커밋

모든 작업을 실행하고 보고서를 만든 뒤 커밋을 처리합니다. 변경된 파일이 없으면(모두 Keep이거나 모든 쓰기가 실패한 경우) 이 단계를 건너뜁니다.

### Git 컨텍스트 확인

선택지를 제시하기 전에 다음을 확인합니다.
1. 현재 체크아웃된 브랜치(main/master인지 feature 브랜치인지)
2. compound-refresh가 수정한 것 외에 작업 트리에 커밋되지 않은 변경이 있는지
3. 저장소의 커밋 스타일에 맞추기 위한 최근 커밋 메시지

### Headless 모드

질문할 사용자가 없으므로 합리적인 기본값을 사용합니다.

| 컨텍스트 | 기본 작업 |
|---------------|---------------|
| main/master에 있음 | 무엇을 refresh했는지 나타내는 이름의 브랜치(예: `docs/refresh-auth-and-ci-learnings`)를 만들고 커밋한 뒤 PR을 열려고 시도합니다. PR 생성이 실패하면 브랜치 이름을 보고합니다. |
| feature 브랜치에 있음 | 현재 브랜치에 별도의 커밋으로 커밋합니다. |
| Git 작업 실패 | 권장 Git 명령을 보고서에 포함하고 계속합니다. |

compound-refresh가 수정한 파일만 stage합니다 — 작업 트리의 다른 변경은 stage하지 않습니다.

### Interactive 모드

먼저 `git branch --show-current`를 실행해 현재 브랜치를 확인합니다. 그 결과에 맞는 선택지를 제시합니다. 어떤 선택지를 고르더라도 compound-refresh 파일만 stage합니다.

**현재 브랜치가 main, master 또는 저장소의 기본 브랜치인 경우:**

1. 브랜치를 만들고 커밋한 뒤 PR을 엽니다(추천) — 브랜치 이름은 일반적인 이름이 아니라 refresh 대상에 구체적이어야 합니다(예: `docs/refresh-auth-learnings`, `docs/compound-refresh`는 사용하지 않음).
2. `{current branch name}`에 직접 커밋합니다.
3. 커밋하지 않음 — 직접 처리

**현재 브랜치가 feature 브랜치이고 작업 트리가 깨끗한 경우:**

1. `{current branch name}`에 별도 커밋으로 커밋합니다(추천).
2. 별도 브랜치를 만들고 커밋합니다.
3. 커밋하지 않음

**현재 브랜치가 feature 브랜치이고 작업 트리가 지저분한 경우(커밋되지 않은 다른 변경이 있는 경우):**

1. `{current branch name}`에 compound-refresh 변경만 커밋합니다(선택적 stage — 다른 변경은 그대로 둠).
2. 커밋하지 않음

### 커밋 메시지

다음 조건을 만족하는 설명적인 커밋 메시지를 작성합니다.
- 무엇을 refresh했는지 요약(예: "오래된 러닝 3개 업데이트, 겹치는 문서 2개 통합, 더 이상 유효하지 않은 문서 1개 삭제")
- 저장소의 기존 커밋 규칙을 따름(최근 Git 로그에서 확인)
- 간결함 — 세부사항은 변경된 파일 자체에 있음

## compound와의 관계

- `compound`는 새로 해결하고 검증한 문제를 포착합니다.
- `compound-refresh`는 코드베이스가 발전함에 따라 오래된 러닝을 유지합니다 — 개별 문서의 정확성과 문서 세트 전체의 설계를 모두 다룹니다.

refresh 과정에 신뢰할 수 있는 후속 문서를 작성할 실제 근거가 충분할 때만 **Replace**를 사용합니다. 근거가 부족하면 stale로 표시하고 사용자가 다음에 문제를 만났을 때 `compound`를 실행하도록 권장합니다.

문서 세트가 자연스럽게 커지고 중복이 생겼다면 **Consolidate**를 적극적으로 사용합니다. `compound`를 실행할 때마다 새 문서가 추가되므로 시간이 지나면 여러 문서가 약간 다른 관점으로 같은 문제를 다룰 수 있습니다. 주기적인 통합은 문서 세트를 간결하고 권위 있게 유지합니다.

## 발견 가능성 검사

refresh 보고서를 생성한 뒤 프로젝트의 지침 파일이 작업을 시작하기 전에 에이전트가 `docs/solutions/`를 발견하고 검색하도록 이끄는지 확인합니다. 이 검사는 매번 실행합니다 — 지식 저장소는 에이전트가 찾을 수 있을 때만 가치가 누적됩니다. 이 검사에서 편집이 발생하면 Phase 5 커밋 흐름의 일부로(또는 바로 뒤에) 커밋합니다 — 아래 5단계를 참조합니다.

1. 루트 수준 지침 파일(AGENTS.md, CLAUDE.md 또는 둘 다)이 어떤 것인지 확인합니다. 파일을 읽고 어떤 파일이 실질적인 내용을 담는지 판단합니다 — 하나는 다른 파일을 `@`로 포함하는 shim일 수 있습니다(예: `CLAUDE.md`가 `@AGENTS.md` 한 줄만 포함하거나 그 반대). 실질적인 파일을 평가 및 편집 대상으로 삼고 shim은 무시합니다. 둘 다 없으면 이 검사를 완전히 건너뜁니다.
2. 지침 파일을 읽은 에이전트가 다음 세 가지를 알 수 있는지 평가합니다.
   - 문서화된 해결책으로 이루어진 검색 가능한 지식 저장소가 존재함
   - 효과적으로 검색할 수 있을 만큼 구조를 알 수 있음(카테고리 구성, `module`, `tags`, `problem_type` 같은 YAML 프런트매터 필드)
   - 언제 검색해야 하는지 알 수 있음(기록된 영역에서 기능 구현, 문제 디버깅 또는 의사결정 전 — 러닝은 버그, 모범 사례, 워크플로 패턴 또는 기타 조직 지식을 다룰 수 있음)

이는 문자열 일치가 아닌 의미 평가입니다. 한 줄의 아키텍처 섹션, gotchas 불릿, 여러 곳에 흩어진 문서화 섹션, `docs/solutions/`라는 정확한 경로를 사용하지 않은 표현도 가능합니다. 지침 파일을 읽은 에이전트가 지식 저장소를 합리적으로 발견하고 사용한다면 검사는 통과합니다.

3. 취지가 이미 충족되었다면 작업이 필요 없습니다.
4. 그렇지 않다면:
   a. 기존 파일의 구조, 어조, 밀도에 따라 언급이 자연스럽게 들어갈 위치를 찾습니다. 새 섹션을 만들기 전에 가장 가까운 관련 섹션(아키텍처 트리, 디렉터리 목록, 문서 섹션 또는 규칙 블록)에 한 줄로 넣을 수 있는지 확인합니다. 기존 섹션에 한 줄을 추가하는 편이 거의 항상 새 heading보다 낫습니다. 명확히 구획된 구조이고 관련 위치가 전혀 없을 때만 최후의 수단으로 새 섹션을 만듭니다.
   b. 세 가지 정보를 전달하는 최소한의 추가 문안을 작성합니다. 기존 문체와 밀도에 맞춥니다. 플러그인이 아니라 지식 저장소 자체를 설명해야 합니다.

      어조는 정보 제공형으로 유지하며 명령형으로 쓰지 않습니다. 시점은 명령이 아니라 서술로 표현합니다 — "구현 또는 디버깅 전에 확인하라"보다 "기록된 영역에서 구현하거나 디버깅할 때 관련 있음"을 사용합니다. "구현 전에 항상 검색하라" 같은 명령형 지시는 워크플로에 이미 전용 검색 단계가 있을 때 중복 읽기를 유발합니다. 목표는 인식입니다. 에이전트가 폴더의 존재와 내용을 알고 언제 참조할지는 스스로 판단하게 합니다.

      다음은 조정 예시이며 템플릿이 아닙니다. 파일에 맞춰 적용합니다.

      기존 디렉터리 목록이나 아키텍처 섹션이 있을 때 — 한 줄 추가:
      ```
      docs/solutions/  # documented solutions to past problems (bugs, best practices, workflow patterns), organized by category with YAML frontmatter (module, tags, problem_type)
      ```

      자연스러운 위치가 전혀 없을 때 — 작은 heading이 적절합니다.
      ```
      ## Documented Solutions

      `docs/solutions/` — documented solutions to past problems (bugs, best practices, workflow patterns), organized by category with YAML frontmatter (`module`, `tags`, `problem_type`). Relevant when implementing or debugging in documented areas.
      ```
   c. Interactive 모드에서는 이것이 중요한 이유를 사용자에게 설명합니다 — 이 저장소에서 작업하는 에이전트(새 세션, 다른 도구 또는 플러그인 없는 협업자 포함)는 지침 파일이 `docs/solutions/`를 드러내지 않으면 확인해야 한다는 사실을 모릅니다. 제안된 변경과 삽입 위치를 보여 주고, 편집 동의를 받기 위해 플랫폼의 차단형 질문 도구를 사용합니다. Claude Code에서는 `AskUserQuestion`(스키마가 로드되지 않았다면 먼저 `select:AskUserQuestion`으로 `ToolSearch` 호출), Codex에서는 `request_user_input`, Antigravity CLI(`agy`)에서는 `ask_question`, Pi에서는 `ask_user`(`pi-ask-user` 확장 필요)를 사용합니다. 하네스에 차단형 질문 도구가 없거나 호출에 실패한 경우(예: Codex edit 모드)에만 채팅에서 제안을 제시합니다. 스키마 로드가 필요하다는 이유로 대체하지 않습니다. 질문을 조용히 건너뛰지 않습니다. Headless 모드에서는 보고서에 "발견 가능성 권장 사항" 줄로 포함하고 지침 파일은 편집하지 않습니다(Headless의 범위는 문서 유지보수이지 프로젝트 설정이 아님).

5. **저장소 루트에 `CONCEPTS.md`가 있으면 이에 대해서도 병렬 발견 가능성 검사를 실행합니다.** 위 `docs/solutions/` 검사와 같은 워크플로를 사용합니다. 같은 대상 파일, 같은 편집 위치 판단, 모드별 동일한 동의 후 편집 상호작용 방식을 적용합니다. 디렉터리 목록이 있을 때의 예:

   ```
   CONCEPTS.md  # shared domain vocabulary — read when orienting to the codebase or before discussing domain concepts
   ```

   **`CONCEPTS.md`가 없으면 이 단계를 완전히 건너뜁니다** — 프로젝트가 채택하지 않은 아티팩트를 요구하지 않습니다. 건너뛸 때 이 단계는 출력도 편집도 만들지 않습니다.

6. **검사에서 편집이 발생하면 커밋을 amend하거나 후속 커밋을 만듭니다.** 4단계 또는 5단계에서 지침 파일을 편집했고 Phase 5에서 이미 refresh 변경을 커밋했다면 새로 편집한 파일을 stage하고 기존 커밋을 amend합니다(같은 브랜치이고 아직 push하지 않은 경우). 이미 원격에 브랜치를 push했다면(예: 브랜치와 PR 경로) 후속 커밋도 push하여 열린 PR에 발견 가능성 변경이 포함되게 합니다. 예: `docs: add docs/solutions/ discoverability to AGENTS.md`, `docs: add CONCEPTS.md discoverability to AGENTS.md`, 또는 두 변경이 함께 들어간 경우 결합된 메시지입니다. 이렇게 하면 실행 종료 시 작업 트리가 깨끗하고 원격과 동기화됩니다. 사용자가 Phase 5에서 "커밋하지 않음"을 선택했다면 별도의 커밋 로직 없이 지침 파일 편집을 다른 refresh 변경과 함께 stage되지 않은 상태로 둡니다.
